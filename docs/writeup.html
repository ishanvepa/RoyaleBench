What the models miss

Across the saved development runs the models rarely fail because they misread the board or break the rules. All 8 attempts in the Win cohort finished with replay integrity 1 and zero rejected actions. They fail on where and when a card goes: a defense that buys too little time, offense sent before the defense holds, a spell timed against the wrong moment, an elixir budget spent on the first threat.

Every row below comes from a saved trace or result file in this repository and says how many attempts it rests on. Where a pattern rests on one attempt, it says so. We name only what the trace shows; where a cause is not visible, the row says that too. Most attempts are single runs, so the counts describe what was seen, not how often it happens.

Background

Clash Royale asks a player to manage a regenerating resource, choose where and when to deploy units, and balance defense against pressure on the opponent's towers. RoyaleBench tests those decisions through exact mid-match continuations in a deterministic simulator, graded by an independent replay.

Resource managementWhen should the agent spend elixir, and when should it save it?
Spatial reasoningWhich placement changes an engagement? Coordinates are never snapped to a legal tile.
Planning and adaptationCan it defend a push and turn the surviving units into a counterattack?

Methodology

Opponent: the Planner

A deterministic search bot: a 10-second look-ahead on a private copy of the engine, three plies, top 4 candidates, 3 answers per candidate, margin 40, elixir valued at 150 HP. It generates its own coordinate placements. It reads the true engine state, including the model's hand and elixir. The model sees its own hand, elixir, the board, visible events and the next card. This information advantage is part of the difficulty and is not a fair fight.

Task construction

  • Fixed state. A position is scripted or saved from the engine and handed to the model. The engine is deterministic: the same decks, seed and commands give the same game.
  • Solvable by construction. Each task has a reference solution found by a privileged search and replayed twice with identical results.
  • Controls. Six cheap or invalid submissions must score zero (wait only, a spell rush, and empty, malformed, wrong-type and partial logs). For v6, all 14 references pass and all 42 controls score zero.
  • No shortcuts. The grader reads the engine's own winner. A seed-parity tiebreak is part of the engine rules. Spending, damage or an HP lead never earn credit on win tasks.

Scoring and variance

The score is mean binary success over tasks. Every result above is one attempt per task. The plan for v7 is three attempts per task to nominate hard tasks and five fresh attempts to confirm them, reported with 95% intervals. Seeds are fixed by each task, so repeats measure model variance only.

Limitations

  • Single attempts, small task counts and no confidence intervals on the numbers above.
  • v5 and the Win cohort were chosen partly because of how Opus and Sonnet performed, so those models' scores on them are not an unbiased estimate. The v7 additions would be selected the same way (tasks Opus fails), so the final set is adversarially chosen and should be tested on at least one other model family.
  • The failure patterns come from saved traces and result files. Where only a final message is stored (GPT-6.1 Sol), the model's reasoning is not available. A pattern is an observation, not a proven cause.
  • The Planner sees hidden information and plays one fixed style. Results describe this simulator, these decks and this opponent. Live-game fidelity and human performance have not been established.
  • Thinking pauses the game, so the benchmark does not measure real-time reaction speed.
  • Scripted play is forbidden by the instructions and checked through diagnostics and trace review, not fully prevented.
  • The Planner finding a winning reference shows a task can be won. It says nothing about how hard it is for a model.
